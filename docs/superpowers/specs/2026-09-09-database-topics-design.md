# 数据库内核独立知识点分支设计

## 1. 状态与依据

用户已确认以下设计方向：

1. 每个知识点一个独立 Git 分支，不采用累进分支。
2. 按可独立学习、验证的算法／机制拆分，关联术语合并。
3. 独立教学实现，C++17，不依赖 BusTub。
4. 已确认聊天中的 82 分支清单及“教学级机制完整”的交付标准。

本文将已确认方案落盘，待用户审阅书面版本后制定实施计划并开始代码实现。

原始需求来源为根目录 `spec.md`。完整、唯一的知识点编号和分支名称清单位于根目录 `README.md`；本文不复制清单，以免两份目录发生分歧。

## 2. 目标与非目标

### 目标

- 覆盖原始资料中 C++ 基础、关系模型、存储、索引、查询处理、优化、事务、恢复以及分布式入门的知识点。
- 每个分支同时交付中文讲解、可运行实现、演示、正确性测试。
- 学习者能够独立检出任一完成分支，构建并验证该知识点。
- 解释数据结构、不变量、执行步骤、成本、失败场景以及实现边界。
- 保留机制本身的关键行为：例如删除中的树再平衡、替换中的 pinned 页保护、恢复中的日志顺序。

### 非目标

- 不将所有主题拼接为生产数据库，不引入统一的大型数据库框架。
- 不复刻指定学期的 BusTub，不保证官方评分器兼容。
- 不实现完整 SQL 标准、完整工业 ARIES 或带自动选主的分布式集群。
- 不把使用标准容器包装的例子当作被学习算法本身的实现；标准容器可用作辅助结构或测试参考答案。
- 不自动添加远端或推送代码。

## 3. 方案取舍

已选择独立教学分支，而不是以下替代方案：

| 方案 | 优点 | 代价／结论 |
| --- | --- | --- |
| 独立教学实现 | 每个主题可单独运行，便于聚焦核心机制 | 少量依赖代码需要随分支附带；采用本方案 |
| 累进式小数据库 | 组件自然集成，能够端到端执行 SQL | 后续主题依赖大量历史代码，不符合独立分支选择 |
| BusTub 项目实现 | 接近官方课程项目与接口 | 版本耦合，且不能覆盖所有知识点；不采用 |

## 4. Git 与文件组织

当前目录初始只有 `spec.md`，不是 Git 仓库。初始化本地 Git，以 `main` 为目录与设计分支。

- `main`：原始资料、知识点总目录、设计和实施计划，以及准确的验收状态。
- `topic/NN-name`：来自共同文档基线的独立实现分支；不得把前一主题的完整提交历史作为学习上的必要依赖。
- 若主题需要底层组件，随分支包含必要实现，解释哪些是支撑代码、哪些是本分支重点。不使用跨分支路径、未提交文件或外部 worktree 作为构建依赖。
- 不为展示数量而提前创建 82 个空实现分支。
- 主题分支根目录 README 改为该主题教程，提供返回总目录的方法；总目录在 `main` 上维护，避免假定分支中的目录副本实时同步。
- 实现分支不合并回 `main`；验收记录和目录状态单独更新到 `main`。
- 构建产物与运行数据不提交。创建新分支和 worktree 前检查路径与名称，避免覆盖用户文件。

单个实现分支采用最小布局：

```text
README.md
CMakeLists.txt
src/
tests/
```

不强制每个概念一个类，不为单个实现引入插件系统、依赖注入框架或通用序列化框架。

## 5. 分支教程内容

每个分支的中文 README 必须回答：

1. 本知识点解决什么问题，属于数据库的哪一层？
2. 前置知识是什么，相关分支有哪些？
3. 核心概念、数据结构、算法步骤与不变量是什么？
4. 用一个具体输入逐步展示执行过程与输出。
5. 关键源码在哪里，怎样构建、运行、测试？
6. 时间／空间／I/O 成本是什么，哪些成本是教学估算？
7. 边界、失败场景、反例是什么？
8. 本实现做了哪些简化，不支持什么，不能据此声称什么？

示意图优先用 Markdown、表格或 ASCII；不额外引入网站或可视化框架。

## 6. 实现与平台约定

- 语言 C++17，构建使用 CMake，测试入口使用 CTest。
- 优先标准库；线程使用标准线程设施及 CMake Threads。
- 默认不添加第三方依赖，不为测试引入大型框架。
- 提供 `demo` 可执行文件和独立的测试目标。
- 测试失败必须返回非零状态；不能只依赖 Release 中失效的 `assert`。
- 默认验证当前 macOS 工具链；保持标准 C++17 部分可移植。使用 POSIX 同步或进程控制的分支明确说明平台限制。
- 持久化主题不得把 `ostream::flush()` 说成稳定存储同步；所用同步调用及其实际保证必须明确。
- 持久化格式验证长度、偏移、类型和损坏输入；处理短读、写入失败及资源释放，避免默默接受损坏数据。
- 测试使用独立临时目录和有界资源，不触碰用户数据文件。

统一入口：

```sh
cmake -S . -B build -DCMAKE_BUILD_TYPE=Debug
cmake --build build
ctest --test-dir build --output-on-failure
./build/demo
```

Release 使用独立构建目录验证。特定主题可以增加实验命令，但不能缺少基础入口。

## 7. 关键语义边界

### 关系与查询

关系代数分支讲集合语义；SQL 与查询算子默认讲明重复行、NULL、结果顺序的处理方式，不能无说明地混用集合与多重集语义。SQL 和窗口函数只实现明确声明的子集，拒绝不支持的语法而不是错误解释。

优化器必须检查规则适用条件，对可改写案例验证结果等价，并对不安全案例保留原计划或明确拒绝改写。聚合下推必须处理重复键对计数的影响，以及 AVG 的 SUM／COUNT 分解。

### 数据结构与存储

哈希及 B+Tree 必须实现所讲算法，标准容器可作为测试 oracle。B+Tree 删除分支必须包含独立运行所需的查找／插入支撑，但教程聚焦删除。

外部排序必须真实生成磁盘有序段，在显式内存预算下归并，不能先将全部输入读入内存。Buffer Pool 必须以真实页 I/O 展示 dirty writeback 与容量约束。

### 并发与事务

并发实现不能用一把全局锁替代所承诺的 latch crabbing。并发测试使用屏障式协调或条件变量构造关键交错，不仅靠 sleep 碰运气。

理论调度、隔离异常可以使用确定性调度模拟器；其身份必须明确，不能据此声称实现真实并发事务系统。真正承诺线程同步的分支必须运行多线程测试。

MVCC 需要明确事务时间戳、已提交／未提交可见性、版本链重建与写写冲突。可串行化 MVCC 可采用保守验证，但必须写明额外中止的代价，并验证其覆盖的冲突类型。

### 恢复

WAL、检查点、Redo／Undo 和 ARIES 教学子集必须有真实文件与进程中断后重启测试。覆盖关键阶段中断、重复恢复，以及 ARIES 分支恢复过程中再次中断。

进程中断不等于断电。说明操作系统缓存、同步调用与存储设备保证的边界，不声称通过进程测试证明了断电安全。

### 分布式入门

Bloom Filter、IVF 和两阶段提交是对原文宽泛分类选定的具体教学算法，非原文逐项指定。

分布式分支可使用明确声明的本地节点与消息模型展示路由、复制、交换和故障；不冒充跨机器生产集群。涉及持久化决策的节点需真实落盘。区分协议步骤演示、线程并行、独立进程和真实网络支持，文档只声称实际具备的能力。

## 8. 验收与状态

每个分支验收至少包含：

1. 从该分支干净检出后独立配置、编译与运行。
2. Debug 与 Release 下测试通过，demo 输出与教程一致。
3. 覆盖正常路径、空输入／边界值以及该机制最重要的反例。
4. 适用时使用朴素参考实现或标准容器作差分验证。
5. 涉及并发、持久化、优化合法性的主题满足第 7 节的专项检查。
6. 教程无未兑现的能力声明，无以 TODO 或伪代码替代核心实现。
7. 记录分支、验收提交、执行命令、测试结果与剩余限制。

目录状态使用“已规划”“实现中”“已验证”。只有完整分支经测试并提交后，才标记“已验证”。部分完成时准确报告数量，不将分支存在当作实现完成。

## 9. 实施顺序与隔离

按根目录的 14 个模块分批实施，优先完成基础主题，随后进入存储、索引、查询、事务与恢复。编号保持稳定，实际实现次序允许根据前置组件调整。

并行开发必须使用独立 worktree，每个 worktree 同时只有一个写入者。`main` 的目录状态由主代理统一更新。依赖主题只有在基础实现已验证后才复用，不能同时读写未完成的共享源码。

先审阅本书面设计，再制定可执行实施计划。实施不得因范围较大而悄悄删减至少数示例，也不得用生成相同空模板的方式充数。
