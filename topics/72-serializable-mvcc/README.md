# 72-serializable-mvcc：保守验证的可串行化 MVCC

## 问题与前置知识

本分支是事务层的独立 C++17 教学实现，不依赖 BusTub 或其他分支。
先了解事务读写、集合、映射和基本串行执行；相关概念可在 `main` 的知识点目录查看。
这里使用**确定性单线程调度模拟**，调用顺序就是交错顺序。没有真实锁等待或线程并发承诺。
模拟的价值是把失败条件固定下来，不依赖 sleep 或操作系统调度运气。

## 原理、不变量与手算轨迹

本分支随附 69／70 的 Undo 链和 SI 支撑源码快照；新增读集与全表谓词令牌验证。
普通读保持 begin 快照并登记键（包括“不存在”的键）；scan 登记 scanned 标志。
提交除 SI 的写写冲突检查外，还检查每个读键的最新时间戳不得超过快照；scan 则要求全表提交时钟未变化。
因此不会因为历史读值稳定就忽略后来的依赖变化。即使最终值被改回原值，时间戳仍能检测冲突。

证明思路：按成功提交顺序串行执行。在每个提交点，验证保证读过的键自快照后没有提交修改，扫描的表也没有变化；于是之前读到的值等于这个串行位置的状态。
所有写在同一次不可交错提交内发布，其他事务看不到部分结果。将自己此前的写叠加到读上，等价于串行事务内部读己之写。
这是保守提交顺序验证，不是 SSI 的危险结构检测，也不是完整谓词锁。

值班轨迹：A/B 快照都看到 alice=bob=1，A 读 bob 并写 alice=0，B 读 alice 并写 bob=0。
A 提交成功；B 的读集含 alice，其新时间戳超过 B 快照，所以 B 中止。demo 输出 `A commits: 1`、`B commits: 0`、`on call: 1`。
幻读型反例：两个事务扫描空预约表，各准备插入不同键；第一人提交后，全表令牌变化，第二人中止。单纯 SI 的写集检查不能发现这种冲突。

全表验证会多中止：即使用户扫描后只关心某个小范围，其他范围的写也会使令牌失效；甚至只读扫描事务也可能中止。
测试专门保留这个额外中止案例，同时验证无关点读／写仍可提交，以及缺失键插入、删除、同键盲写和读己之写。

## 源码导读

- `src/tutorial.hpp`：核心状态与算法；先读数据成员，再按 demo 顺序跟踪状态转换。
- `src/demo.cpp`：小型可重现调度，输出最终状态／判定，不是算法的替代品。
- `tests/test.cpp`：独立正例、冲突反例与边界测试；`check` 失败抛异常，main 返回非零，Release 同样有效。
- `CMakeLists.txt`：无第三方库的 demo 与 CTest 入口，禁用编译器语言扩展。

把读操作、写操作及提交操作分开，是为了观察“读到什么”和“最终能否提交”并非同一个问题。
学习时可交换测试中的两次调用，手算结果，再运行测试验证；不要把一次成功调度当成所有调度都安全的证明。

## 成本

沿用 O(v) Undo 重建；增加 r 个读键检查 O(r log n)，全表令牌 O(1)。扫描／提交复制仍为全表及历史量级 O(n+H)（容器插入另含 log 因子）；读集空间 O(r)。

## 构建、测试与预期结果

```sh
cmake -S . -B build -DCMAKE_BUILD_TYPE=Debug
cmake --build build -j2
ctest --test-dir build --output-on-failure
./build/demo
cmake -S . -B build-release -DCMAKE_BUILD_TYPE=Release
cmake --build build-release -j2
ctest --test-dir build-release --output-on-failure
./build-release/demo
```

两种模式均应显示 CTest 1/1 通过；直接运行测试输出 `all checks passed`。
demo 的数值含义见上面的具体轨迹，布尔值使用 0/1。
若 macOS 的 AppleClang 报标准库头文件不存在，可仅在本机配置时附加：

```sh
cmake -S . -B build -DCMAKE_BUILD_TYPE=Debug \
  -DCMAKE_CXX_FLAGS="-isystem $(xcrun --show-sdk-path)/usr/include/c++/v1"
```

Release 配置可附加相同参数；不需要改系统文件或把 SDK 路径写进项目。

## 局限与不能推出的结论

全表版本令牌代替精确范围验证，存在额外中止；不是 SSI。未实现历史回收、真正线程同步、重试调度或事务读阶段的完整 opacity 保证。

所有状态仅存内存，没有 WAL、磁盘同步、崩溃恢复或跨进程保证。
标准容器仅存储事务元数据；被讲解的冲突规则与状态转换在源码中直接实现。
此示例不提供 SQL、网络服务或生产系统的资源管理；调用者必须使用规定的生命周期。
